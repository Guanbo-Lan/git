轻客管家

项目架构 & 一次请求的完整旅程

一、三大模块，各司其职

qk-common

后勤行政部
  • 统一返回 Result
  • 全局异常处理
  • JWT 工具 / 登录拦截器
  • 分页 / 静态资源配置

qk-entity

数据模型
  • PO —— 对应数据库表
  • DTO —— 接收前端参数
  • VO —— 返回给前端
  • 只定义结构，不写逻辑

qk-management

业务实干部
  • Controller 接请求
  • Service 写业务
  • Mapper 读写数据库
  • 启动类 QKApp

二、一次请求的完整旅程

1
浏览器 / 前端 发起请求
发出 HTTP 请求，请求头里带上登录拿到的 Token。
POST /login  { "username":"...", "password":"..." }
▼
2
登录拦截器 门卫 · LoginInterceptor
检查请求头 Token：为空或验签失败就直接拦下，返回 401。
放行名单：/login 和 /upload/**。
无 Token → 401
▼
3
Controller 层 服务员
接收参数 → 调用 Service → 用 Result 统一包装返回。不写业务逻辑。
return Result.success(vo);
▼
4
Service 层 厨师
真正的业务逻辑：校验、判断、组装数据。遇到不合法的情况直接抛异常。
if (用户不存在) Throws.throwE(PARAM_INVALID);
▼
5
Mapper 层 仓库管理员
继承 MyBatis-Plus 的 BaseMapper，单表增删改查一行不用写，自动生成。
public interface UserMapper extends BaseMapper<User> { }
▼
6
MySQL 数据库 qk
数据最终落到表里：user、dept、role、clue、business、customer ...

三、两个横向机制（所有接口都靠它们）

统一返回

Result —— 格式永远一样

成功 code=1，失败 code=0。前端只写一次解析逻辑。
构造器私有，只能 success() / error() 创建。

全局异常处理

QkExceptionHandler —— 异常的收容所

业务代码「该抛就抛」，不用写 try-catch。
业务异常给真实原因，其它异常兜底提示。

→
客户已成交
